# ChatGPT development guide

This file defines the architectural and documentation conventions for this
repository. Treat these as project rules when changing the library.

The model, code and documentation are being developed with the assistance of
ChatGPT.

## 1. Repository purpose

`lib.scad.clamps` is a reusable CAD library for clamp components.

The first component is `tube-clamp`, implemented in parallel in:

```text
openscad/tube-clamp/
pythonscad/tube-clamp/
```

The two implementations should represent the same design and expose the same
concepts, but they do not need to use identical language constructs.

Prefer the natural idioms of each language over forced syntactic symmetry.

## 2. Source, design and verification

Keep these concerns separate:

```text
source / design docs / tests -> main
generated verification      -> verification branch
```

Design images are generated from design render entrypoints.

Functional verification output is generated by GitHub Actions and published to
the orphan `verification` branch. Do not commit generated verification output
to `main`.

Generated PNGs and STL verification artifacts should not be included in ZIP
deliverables created during development.

## 3. OpenSCAD API philosophy

OpenSCAD does not have conventional classes, so use its object support in a
C-struct-like way.

The public pattern is:

```scad
clamp = tube_clamp_create(...);

tube_clamp_build(clamp);
tube_clamp_render(
    clamp,
    view = TUBE_CLAMP_VIEW_OPENING
);

inner_r = tube_clamp_inner_radius(clamp);
outer_r = tube_clamp_outer_radius(clamp);
```

### Public API naming

Use a common component prefix:

```text
tube_clamp_create
tube_clamp_build
tube_clamp_render
tube_clamp_inner_radius
tube_clamp_outer_radius
```

Do not rename the create/build/render lifecycle without an explicit API
decision.

### Object creation

All primary parametric inputs belong in `tube_clamp_create(...)`.

The returned OpenSCAD object is the data model passed through geometry and
calculation functions. Avoid repeatedly passing long lists of individual
parameters through helper modules.

### OpenSCAD object feature

`object()` is currently experimental and requires:

```bash
openscad --enable=object-function ...
```

All repository scripts that invoke OpenSCAD must enable this feature.

Do not replace the object API with arrays or positional structures merely to
avoid this flag unless the project explicitly decides to abandon the object
model.

## 4. PythonSCAD API philosophy

PythonSCAD should use native Python object-oriented design rather than copying
the OpenSCAD/C-style API literally.

The main API is:

```python
clamp = TubeClamp(
    tube_diameter=20,
    clearance=0.0,
    wall_thickness=3,
    clamp_width=16,
    opening_angle=60,
)

clamp.build()
clamp.render(view=TubeClamp.View.OPENING)

clamp.inner_radius
clamp.outer_radius
```

### Constructor

The `TubeClamp(...)` constructor is the complete parametric input surface of the
Python model.

Do not add a redundant `tube_clamp_create()` factory unless there is a real
need for one.

### Methods and properties

Use:

```text
build()               final geometry
render(view=...)      design/debug visualization
inner_radius          derived property
outer_radius          derived property
```

Private construction details should normally be private methods such as:

```text
_full_ring()
_opening_cutter()
```

## 5. View naming

### OpenSCAD

OpenSCAD global names must be prefixed to avoid collisions when multiple
libraries are used together.

Use:

```scad
TUBE_CLAMP_VIEW_FINAL = 0;
TUBE_CLAMP_VIEW_RING = 1;
TUBE_CLAMP_VIEW_OPENING = 2;

TUBE_CLAMP_VIEW_TABLE = [
    [TUBE_CLAMP_VIEW_FINAL,   "Final clamp"],
    [TUBE_CLAMP_VIEW_RING,    "Full ring"],
    [TUBE_CLAMP_VIEW_OPENING, "Opening cutter"]
];
```

The enum value is intentionally also the table index.

Keep the consistency check:

```scad
function tube_clamp_view_label(view) =
    assert(
        TUBE_CLAMP_VIEW_TABLE[view][0] == view,
        "TUBE_CLAMP_VIEW_TABLE index/value mismatch"
    )
    TUBE_CLAMP_VIEW_TABLE[view][1];
```

`TABLE` is preferred over `CONFIG` for this lookup structure.

The Customizer uses the same numeric values.

### PythonSCAD

Use a native enum scoped inside the class:

```python
class View(StrEnum):
    FINAL = "Final clamp"
    RING = "Full ring"
    OPENING = "Opening cutter"
```

Do not recreate the OpenSCAD numeric table in Python.

The enum values are already the readable labels, so do not add a duplicate
label table.

The render entrypoint must convert externally supplied command-line values to
the enum before rendering.

## 6. Surface resolution

Surface resolution is a render/model setting, not part of the clamp geometry
API.

OpenSCAD:

```scad
$fn = 120;
```

PythonSCAD:

```python
fn = 120
```

Render entrypoints must set their own resolution as well. Do not pass a
`segments` parameter through the public geometry API.

## 7. Design documentation

Each implementation has a `design/design.md` explaining the design.

The purpose is to document the geometry and important implementation choices,
not to duplicate the full source file.

A good design section contains:

1. a short explanation of the construction step;
2. the essential code snippet that explains the geometry;
3. the generated design image.

For the tube clamp the design sequence is:

```text
01-ring
02-opening
03-final
```

The important opening view shows:

- the complete ring;
- the opening cutter as a transparent red overlay.

Keep OpenSCAD and PythonSCAD design images conceptually equivalent.

Do not reduce `design.md` to only images, but also do not turn it into a full
line-by-line code walkthrough.

## 8. Surface colors in design views

For the opening construction view:

```text
ring   -> neutral/light gray
cutter -> red, transparent
```

PythonSCAD must explicitly color the ring in construction views because its
default object color differs from OpenSCAD.

The final model does not need to inherit debug/construction colors.

## 9. PythonSCAD module imports

PythonSCAD uses normal Python imports.

The official PythonSCAD examples document adding external module locations to
`sys.path`:

https://www.pythonscad.org/examples/

Example from the documentation:

```python
import sys
sys.path.append("\\path\\to\\python\\site-packages-dir")
```

The repository consumer test uses the same mechanism with a repository-relative
path.

Do not use `osuse()` for importing the native `tube_clamp.py` module.
`osuse()` is for consuming OpenSCAD libraries from PythonSCAD.

## 10. Functional consumer tests

Tests under `test/` must use the public API as an external consumer would.

Current structure:

```text
test/
├── openscad/
│   └── tube_clamp_api.scad
└── pythonscad/
    └── tube_clamp_api.py
```

The functional test creates three clamps with clearly different dimensions.

It should verify both:

- geometry can be rendered/exported;
- derived calculations return expected values.

Tests should not directly call private helpers.

## 11. Verification workflow

The verification workflow should:

1. run the OpenSCAD consumer test;
2. run the PythonSCAD consumer test;
3. render PNG output;
4. export STL output;
5. fail on real command failures and logged `ERROR:` messages;
6. publish only successful output;
7. publish to the orphan `verification` branch.

A failed verification run must not replace the last successful verification
output.

### Shell scripts in GitHub Actions

Do not rely on Unix executable bits being preserved when repository snapshots
are prepared from Windows or ZIP files.

Invoke repository shell scripts explicitly:

```yaml
run: bash scripts/run-verification.sh
```

instead of:

```yaml
run: scripts/run-verification.sh
```

## 12. Naming conventions

Use:

```text
repository/directory names -> kebab-case
code filenames             -> snake_case
OpenSCAD modules/functions -> snake_case
Python names                -> normal Python snake_case / PascalCase classes
```

Examples:

```text
tube-clamp/
tube_clamp.scad
tube_clamp_render.scad
tube_clamp.py
tube_clamp_render.py
TubeClamp
```

OpenSCAD public global constants must include the component prefix, for example:

```text
TUBE_CLAMP_VIEW_FINAL
TUBE_CLAMP_VIEW_TABLE
```

This prevents collisions between future libraries.

## 13. Public versus private helpers

OpenSCAD has no strict private namespace. Prefix implementation-only helpers
with `_`.

Python uses normal private-method convention with `_`.

Keep the public surface small. Add a public calculation function/property when
it represents useful component information, not merely because an internal
helper exists.

## 14. Parallel implementation principle

OpenSCAD and PythonSCAD should stay conceptually comparable:

```text
OpenSCAD                        PythonSCAD

tube_clamp_create(...)          TubeClamp(...)
tube_clamp_build(clamp)         clamp.build()
tube_clamp_render(clamp, view)  clamp.render(view)
tube_clamp_inner_radius(clamp)  clamp.inner_radius
tube_clamp_outer_radius(clamp)  clamp.outer_radius
```

Do not force both languages to use the same mechanics merely for visual
symmetry.

The goal is equivalent design behavior with idiomatic APIs.

## 15. Change discipline

This repository has accumulated deliberate architectural choices. When changing
one concern, avoid silently rewriting unrelated decisions.

Before a refactor:

1. inspect the current source rather than relying on an older iteration;
2. identify which API/documentation/workflow pieces are affected;
3. preserve unrelated behavior;
4. update source and relevant design documentation together;
5. keep functional consumer tests aligned with the public API.

Prefer a focused change over broad opportunistic cleanup.
